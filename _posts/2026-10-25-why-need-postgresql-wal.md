## WAL은 왜 존재하나

### WAL이 없으면 생기는 딜레마

DB는 아래 두 가지 원칙을 지켜야 합니다.

- 내구성: "COMMIT 완료"라고 답한 변경은 물리적으로 절대 사라지면 안됩니다.
- 성능: 초당 수천 건의 트랜잭션을 처리할 수 있어야 합니다.

WAL 없이 위 두 가지 원칙을 지키는 것은 어렵습니다. WAL 없이 할 수 있는 선택과 그로인한 결과를 살펴보겠습니다.


| 선택                                    | 결과                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------- |
| 커밋마다 바뀐 데이터 전부를 디스크에 쓴다.              | 내구성 조건은 만족할 수 있다. 하지만 테이블, 인덱스 파일에 흩어진 페이지를 매번 랜덤 쓰기 + fsync 해야해서 매우 느리다. |
| 데이터 페이지는 메모리에 두고 나중에 한번에 몰아서 디스크에 쓴다. | 성능은 매우 빠르다. 하지만 정전과 같은 물리적 이슈 발생시 "COMMIT 완료"라고 답한 트랜잭션의 데이터 변경이 유실된다.    |
| 디스크 쓰기 작업 도중 정전이 발생한다.                | 테이블 파일은 변경되었는데 인덱스 파일이 변경되지 않을 수 있다. 페이지 하나가 반만 써질 수 있다.                  |


WAL은 위 딜레마를 풀기 위해 **TODO 리스트를 작성하는 것**이라고 생각하면 좋을 것 같습니다. 클라이언트에서 데이터 수정, 삽입, 삭제를 요청하는 경우 원본 데이터 파일부터 건드리는 것이 아니라 데이터 파일에 대해서 해야할 일들을 미리 적어두는 것이죠. Write Ahead Log라는 이름을 살펴보면 그 의도가 담겨 있습니다. *"쓰기 전에 로깅부터"*

### 크래시 복구 - 내구성

**Write-Ahead 규칙**

1. 커밋 규칙: "COMMIT 완료"라고 답하기 전에 해당 트랜잭션의 COMMIT 레코드가 WAL 파일에 쓰여있어야 합니다.
2. 페이지 쓰기 규칙: Dirty 데이터 페이지를 디스크에 쓰기 전에 그 페이지를 바꾼 WAL 레코드가 반드시 디스크 WAL 파일에 쓰여있어야 합니다.

(기본 설정인 `synchronous_commit=on`, `fsync=on`을 전제로) PostgreSQL은 COMMIT 레코드가 포함된 WAL을 영구 저장소에 플러시한 뒤 클라이언트에게 커밋 완료를 응답합니다. 이때 변경된 데이터 페이지까지 디스크에 쓸 필요는 없습니다. 반대로 **커밋되지 않은 변경이 담긴 데이터 페이지도 디스크에 쓰일 수 있습니다.** 페이지 쓰기 규칙이 보장하는 것은 해당 변경의 WAL이 데이터 페이지보다 먼저 저장된다는 점이지, 커밋 여부에 따라 페이지 쓰기를 막는다는 뜻이 아닙니다. [PostgreSQL WAL 문서](https://www.postgresql.org/docs/17/wal-intro.html)

2번 규칙은 어떻게 만족되고 있을까요? 모든 데이터 페이지의 헤더에는 "이 페이지를 마지막으로 변경한 WAL 레코드의 LSN"(`pd_lsn`)이 적혀 있습니다. 메모리에 올라가 있는 dirty 데이터 페이지를 디스크에 쓰려고 할 때, 해당 LSN까지의 WAL이 먼저 영구 저장소에 플러시되도록 합니다. **즉, 데이터 파일의 변경 사항보다 그 변경을 설명하는 WAL이 먼저 저장됩니다.**

그렇다면 이제 크래시 발생 후 복구가 어떤식으로 이루어지는지 살펴봅시다.

![체크포인트 이후 WAL을 재생해 커밋된 트랜잭션을 복구하는 과정](/assets/img/postgresql-wal-crash-recovery.png)

1. 디스크의 WAL 파일을 마지막 체크포인트 시점부터 순차적으로 읽습니다. 
2. T1과 T2 트랜재션의 커밋 기록이 WAL 파일에 있기 때문에 복구 대상입니다. 1번 커밋 규칙에 따라서 T1, T2 세션은 "COMMIT 완료"를 응답받았기 때문에 더더욱 복구 대상입니다. 
3. T3는 비록 세션에서 커밋 명령어를 날렸지만 아직 메모리에만 기록되고 flush되지 않아 디스크에 기록되지 않았습니다. 따라서 복구 대상이 아닙니다.
4. T4는 세션에서 커밋없이 진행되던 작업이었기 때문에 복구 대상이 아닙니다.

### 왜 빠른가?

WAL이 존재함으로써 DB의 성능 향상, 특히 쓰기 작업에서의 성능 향상을 얻을 수 있습니다. UPDATE를 비교해보겠습니다.

||데이터 페이지 직접 flush|WAL|
|----|----|----|
|파일|힙, 인덱스, pg_xact 등 여러 개|WAL 세그먼트 1개|
|크기|페이지 단위 (8kB × N)|레코드 단위 (수백 바이트)|
|fsync|파일 수 만큼|1번|

Group commit 기능을 통해서도 성능 향상을 얻을 수 있습니다.

1. 버퍼 - 동시에 여러 트랜잭션

여러 트랜잭션이 동시에 INSERT하여도 WAL 버퍼에 자기 레코드가 들어갈 자리를 짧게 예약하고, 그 자리에 레코드를 복사합니다. 여러 개의 가벼운 락으로 나뉘어 있어서 동시에 많은 백엔드가 병렬로 끼워 넣을 수 있습니다. 이 단계는 메모리 작업이라 빠릅니다.

2. 디스크 - 한번에 한명만

디스크로 내리는 작업은 WALWriteLock이라는 락 하나로 직렬화돼 있습니다. 커밋하는 백엔드는 대략 이런 로직을 탑니다(XLogFlush를 단순화한 것):

```
XLogFlush(내 COMMIT 레코드 LSN):
  1. 이미 디스크에 flush된 위치 ≥ 내 LSN 이면 → 바로 리턴 (할 일 없음)
  2. WALWriteLock 획득 (다른 누가 flush 중이면 여기서 대기)
  3. 락을 얻은 뒤 다시 확인: 그새 누가 내 LSN까지 flush해 줬으면 → 락 풀고 리턴
  4. 아니면 "현재 WAL 버퍼에 삽입돼 있는 끝"까지 전부 write + fsync
     (내 LSN까지만이 아니라, 그 뒤에 들어온 남의 레코드까지 한꺼번에)
  5. flush 위치 갱신, 락 해제
```

포인트는 4번이에요. 락을 잡은 백엔드는 자기 것만이 아니라 그때까지 버퍼에 들어온 모든 레코드를 같이 내립니다. 그리고 락을 기다리던 다른 백엔드들은 3번에서 "어, 이미 내려갔네" 하고 fsync 없이 끝나요.

시간 순서로 보면 이렇습니다(fsync 4ms 가정).
```
0.0ms  A: COMMIT 레코드 삽입 (LSN 100) → 락 획득 → 100까지 fsync 시작
0.5ms  B: COMMIT 레코드 삽입 (LSN 120) → 락 대기
1.2ms  C: COMMIT 레코드 삽입 (LSN 140) → 락 대기
2.0ms  D: COMMIT 레코드 삽입 (LSN 160) → 락 대기
4.0ms  A: fsync 완료, 락 해제 → A 커밋 응답
4.0ms  B: 락 획득 → 확인: flush 위치 100 < 120 → 버퍼 끝(160)까지 fsync 시작
8.0ms  B: fsync 완료 → B 커밋 응답
8.0ms  C: 락 획득 → 확인: flush 위치 160 ≥ 140 → fsync 없이 커밋 응답
8.0ms  D: 락 획득 → 확인: 160 ≥ 160 → fsync 없이 커밋 응답
```

8ms 동안 fsync 2번으로 커밋 4개. 하나씩 했다면 16ms가 걸렸을 겁니다. 동시에 기다리는 트랜잭션이 많을수록 fsync 한 번이 처리하는 커밋 수가 늘어납니다.

데이터 페이지 방식에서는 A, B, C, D가 바꾼 페이지는 서로 다른 파일의 다른 위치라서, A의 페이지를 flush해도 B의 페이지는 보장되지 않습니다. 모두가 하나의 순차 스트림에 쓰기 때문에, 뒤쪽 위치 하나를 보장하면 앞쪽은 자동으로 보장되는 WAL의 구조 덕분에 가능한 일입니다.
